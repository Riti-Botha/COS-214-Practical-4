SECTION: DESIGN / OWNERSHIP RATIONALE — State Pattern
================================================================

dispatchAmbulance models a single emergency-response vehicle task. Its behaviour must
change as it moves through a realistic lifecycle, and invalid actions must be rejected
rather than silently accepted or allowed to crash the program. This is a direct fit for
the State pattern rather than a flag/enum with if-else checks, since the number of
lifecycle stages and the rules between them are non-trivial (6 states, some with no
valid outgoing transition for a given event).

Lifecycle modelled: Pending -> Dispatched -> En Route -> On Scene -> Completed, with
Cancelled reachable from Pending, Dispatched, or En Route only (a unit already
committed on scene can no longer be cancelled).

Ownership: dispatchAmbulance (the Context) owns exactly one TaskState* (currentState)
at a time. Every transition deletes the previous state object before assigning the new
one, and the destructor deletes whatever state is active when the object is destroyed.
This gives a single, clear owner for each TaskState instance and avoids any possibility
of a dangling reference to a previous state.

Invalid transitions are handled by having each concrete state implement all four
lifecycle actions (dispatch/arrive/complete/cancel): valid ones transition to the next
state, invalid ones print a rejection message identifying the task, the attempted
action and the current state, and leave the object's state unchanged. This satisfies
the requirement that invalid actions or transitions be "handled sensibly" without
resorting to type checks or a centralised if/else chain — every class only needs to
know how to handle its own four events.

SECTION: GDB BUG INVESTIGATION AND VALGRIND EVIDENCE
================================================================

Note for PDF assembly: this section is the targeted bug investigation for the State
pattern specifically. It complements, rather than duplicates, Member 1's full-application
Valgrind evidence (docs/member1-valgrind-evidence.pdf), which shows the final taskforge
executable running clean end to end (140 allocs, 140 frees, 0 errors). The numbers in
that evidence match the "Verification" step below exactly, confirming the fix holds at
both the isolated-bug level and the full-application level. Place Member 1's screenshot
first, then this write-up, in the final Task 5 section.

Bug: memory leak in dispatchAmbulance::setState() during lifecycle transitions.

Symptom:
Running a sequence of valid lifecycle transitions (dispatch -> arrive -> arrive ->
complete) and checking with Valgrind inside the project's Docker container reported:

    ==HEAP SUMMARY==
        in use at exit: 32 bytes in 4 blocks
    ==LEAK SUMMARY==
        definitely lost: 32 bytes in 4 blocks

32 bytes across 4 blocks — exactly one TaskState object leaked per transition performed.

Cause:
dispatchAmbulance::setState() reassigned the currentState pointer to the new state
object without deleting the previous one first:

    void dispatchAmbulance::setState(TaskState* newState) {
        currentState = newState;   // old currentState pointer overwritten and lost
    }

Debugging process (GDB, run inside the project's Docker container):
A breakpoint was set on dispatchAmbulance::setState. On the first hit, currentState
(the original PendingState) and newState (the incoming DispatchedState) were printed,
then the assignment was stepped over and currentState printed again:

    Breakpoint 1, dispatchAmbulance::setState (this=0x..., newState=0x...39320) at composite.cpp:17
    17          currentState = newState;
    $1 = (TaskState *) 0x...382f0    <- original PendingState
    $2 = (TaskState *) 0x...39320    <- incoming DispatchedState
    (next)
    $3 = (TaskState *) 0x...39320    <- currentState now points here;
                                         0x...382f0 is never referenced again

This matched Valgrind's reported loss record for the PendingState allocation exactly,
confirming the cause.

Correction:
    void dispatchAmbulance::setState(TaskState* newState) {
        delete currentState;
        currentState = newState;
    }

Verification:
Re-running Valgrind (in Docker) against the same transition sequence, and separately
against the full taskforge executable and its runtime scenarios, both reported:

    ==HEAP SUMMARY==
        in use at exit: 0 bytes in 0 blocks
    ==ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)

All GDB and Valgrind evidence above was reproduced inside the project's supplied
Docker environment (taskforge-env), not just on the host machine, per Rule 10.
